# Desktop shell (`landing/desktop.html`)

> The Start menu, taskbar, window mode, the 5s desktop heartbeat, PWA/service
> worker, warning banner, and mobile ergonomics. Apps hosted by this shell:
> `docs/apps.md`.

## The shell

The root page at `/` is a Windows-style shell:
- **Start button** — always present at the taskbar's left. Clicking it toggles the **Start menu**, a launcher listing seven everyday apps (Terminal, Browser, X11 Launcher, Files, Office, Notes, Upload), then a separated **System** subsection with the **Update** app (set apart since it's rarely used) and the **Utilities** flyout, each with icon + description. Picking one opens it. (This replaced the old always-pinned tab bar.) **Services** (in the Utilities flyout — Start ▸ Utilities ▸ Services) is an **auto-discovering network-service dashboard** (`landing/index.html`, served at `/landing.html`) — it lists the host's other web services (Ollama/Open WebUI, ThinLinc, Streamlit apps, Jupyter, …) with **zero config**. The manager's `GET /api/services/discover` (sibling module `terminal/service_discovery.py`) scans listening TCP sockets (`ss -tlnp`), keeps those bound to a **non-loopback** address (a process on `0.0.0.0`/`::` is a network service; loopback-only sockets — incl. all of vibetop's own internals — are excluded), drops infra ports/daemons (ssh/smtp/dns/rpc/db + vibetop's own `:80`), and **names each from its `/proc/<pid>/cmdline`** (a recognizer table for well-known apps → a port hint → `proc :port`; the *effective* program is pulled from the cmdline when the socket owner is a generic interpreter like `python3`, so `python3 …/vsmagent` is filtered and `python3 …/open-webui` is named "Open WebUI"). Each card's dot is green (it's listening); tapping a card opens the service in the **embedded Browser** (Chromium runs on the host, so it reaches the LAN service whether you're on the LAN or coming through the tunnel), with a `↗ new tab` link for LAN clients. Data comes from a direct `/api/services/discover` fetch (LAN) or a parent `postMessage` relay (tunnel). This replaced the old hand-maintained, gitignored `services.json` (which in practice stayed the shipped example — hence the rebuild). Result memoized ~5s server-side.
- **Taskbar apps** — only *opened* apps get a button (Windows-style), each with a close (×). Multiple apps can be open at once; the focused one is highlighted with a per-app accent underline. Buttons are **drag-reorderable** (HTML5 DnD — desktop only; it's a no-op on touch so tap/scroll are unaffected): dragover reshuffles the DOM live, dragend reads the new order back into `openApps` and persists it. App-switching is wired on **`pointerdown`** for mouse (close × and touch stay on `click`) for the same reason as the terminal tabs — a focused app iframe makes the browser eat the first taskbar click moving focus back to the parent, so click-based switching needed two clicks. The set of open apps, their order, and the active one are persisted **server-side** via `GET/POST /api/desktop` (file `~/.local/share/desktop-state.json`). **Windows are local to each instance** — opening an app on the phone does NOT open a window on the computer (window mirroring was tried and removed: the Browser is a single shared-size xpra display, so a wide desktop client connecting would force desktop layout onto the phone, and windows silently appearing is jarring). What *is* shared across instances: (1) the Start-menu **"running" dots show the UNION** of apps open on any live instance (awareness), (2) a **logout/reset clears every instance**, and (3) **close-on-all-devices** — a running app's Start-menu row shows a soft **⏻ power button** (only when running; a real tap-target, confirmed) that closes that app on *every* client (the one place an app open only on another device is reachable). Each browser has a stable `INSTANCE_ID` (localStorage); the manager keeps a **per-instance registry** (`{instances:{id:{open,active,ts}}, reset_epoch}`) — a 5s heartbeat (`pushDesktop`, plus a re-register on `visibilitychange`) keeps an instance in the "live" union (`DESKTOP_TTL` 120s — must exceed browsers' ~60s background-tab timer throttling or an idle machine's dots wrongly go dark elsewhere), and the same id lets a device **restore its own windows** (`GET /api/desktop?instance=`) on reload, not the other device's. Closing via the taskbar × is local (drops from this instance's set; the dot goes dark once no live instance has it). To close across devices, the Start-menu ✕ calls `POST /api/desktop/close {app}`, which records the **live instances that currently have the app open** in `close_targets` (`{appId:[instanceId,…]}`); each instance closes the app when it sees its own id listed in a heartbeat reply, then reports an open-set without it and the server prunes it out (also pruned when an instance goes stale). Targeting by instance id (not a global flag/counter) means **reloading the holding device still closes it**, and a stuck holder can't poison the app for other devices. `/api/reset` bumps `reset_epoch`; every other instance sees it advance on its next heartbeat and tears its own desktop down (`clearAllLocal`). On a fresh desktop with nothing open the Start menu auto-opens.
- **App frames** — each app is an iframe (full-viewport by default; a floating window in **Window mode**, below), **created** on first open but only `src`-loaded on first activation (`loadIfNeeded`) so the inner content always measures the real viewport (otherwise xterm.js / FitAddon initialise at 0×0 and the terminal renders truncated). Closed apps are **removed from the DOM** (true unload). All iframes carry `allow="clipboard-read; clipboard-write"` for cross-iframe clipboard.
- **Window mode (v1.19.x) — floating, movable, resizable windows; OPT-IN, default OFF.** The default desktop is still the classic full-screen one-app-at-a-time switcher (v1.19.0 shipped windows default-on; **v1.19.2 reverted that on purpose**). Turn it on with the **🗔 button in the taskbar** (next to Start; one tap, applied live), at **Start ▸ Utilities ▸ "Floating windows"** (the same toggle, with a sentence explaining what changes), or with **`?wm=1`** / `?wm=0`, which **stick** (persisted, so it's a one-time switch, not a per-visit flag). **The label is "Floating windows"** — it names what turns on rather than a mode. ("Stage Manager" was considered and rejected: that names Apple's thumbnail-rail paradigm, which this is not.) The 🗔 button shows whenever the screen is window-**capable** (`windowModeCapable()`, split out of `windowModeOn()` for exactly this), on or off — a switch only findable once already on is no switch; it previously lived two levels deep in the Utilities flyout. `applyWinModeMenu()` syncs BOTH surfaces so they cannot disagree.
  - **It is device-local** — `localStorage['vibetop:wm']` for the flag, `localStorage['vibetop:wins']` for per-app geometry. This is the odd one out among the shell toggles: **System Stats and Claude Usage are shared across clients** via `POST /api/desktop/ui` + the heartbeat, but window mode and window geometry are **not** synced and have no server field. That's deliberate and matches "windows are local to each instance" above — a phone and a 4K desktop want different layouts.
  - **Gated by screen SIZE, not touch** (`windowModeOn`), on **both** sides: `min(w,h) >= 600 && max(w,h) >= 900`, plus a fine-pointer arm (`w >= 900 && pointer:fine`) so a short, wide desktop window keeps windows. Tablets/iPads get windows in **both orientations**; phones never do. A long-side-only test cannot work — Pixel 9 Pro landscape is 900×375 — and the old `max >= 1000 || w >= 900` missed the 656×944 iPad gen 11 in portrait, so windows vanished when that iPad was rotated (v1.19.10). Touch drag/resize works via enlarged grips + `touch-action:none` under `body.is-touch`.
  - **Structure, load-bearing:** each iframe is wrapped **once** in a `.win` container and **never reparented**, so xpra/terminal state and the deferred-`src` 0×0 fix survive. The explicit height chain `.win{inset:0}` → `.win-body{flex:1}` → `iframe{height:100%}` matters: a replaced `<iframe>` with `height:auto` collapses to its intrinsic ~150px — the exact bug that killed an earlier tiling attempt. Default/mobile render the **same DOM** as a chromeless full-bleed window (verified pixel-identical), so there is one code path, not two.
  - **Pure geometry lives in `landing/winmgr.js`** (`window.VibeWin`; DOM-free like `terminal/lib/tab-sync.js`, unit-tested by `winmgr.test.js`): `clampGeom`, `resizeGeom` (per-direction), `defaultGeom` (cascade), snap, `tileGrid`. `desktop.html` does only the DOM/pointer glue — **keep new geometry decisions in `winmgr.js`** where they're testable.
  - **Gestures:** **click anywhere in a window** to focus + raise it (the parent listens on each same-origin frame's `contentDocument` — iframe events don't bubble, so before v1.19.10 only the title bar, the 5px edges and the taskbar raised a window); drag the title bar to move; drag any of 8 edges/corners to resize (visible diagonal SE grip, v1.19.4); **▢** or **double-tap the title bar** to maximize/restore (▢ becomes **❐ "Restore"** while maximized); **–** to minimize; drag to a side edge (28px mouse / 48px touch) to snap to a half. Edge-snap is **halves only** — top-edge snap-to-maximize was removed (▢ already does it). The double-tap is detected from two `pointerdown`s (<400ms, <24px), not `dblclick` — but **decided on pointerUP**, only if the gesture moved <10px, or "tap the title bar, then drag" maximizes instead of moving.
  - **The title-bar buttons act on `pointerdown`+`pointerup`, NOT `click`** — they carry `tabindex` for keyboard access, which makes WebKit focus the span on pointerdown, and `setActive()` then moves focus into the app iframe mid-gesture so **WebKit dispatches no `click` at all**. Measured on iPad; don't move them back. Enter/Space work via a `keydown` handler.
  - **Taskbar semantics in window mode:** a minimized window's button is dimmed (`.task-app.minimized`), clicking the focused app's button minimizes it, and clicking a minimized one restores it (`taskbarToggle`) — in the classic desktop `setActive(null)` *is* minimizing, but with every window visible that only dropped the focus highlight.
  - **Opening a 2nd app auto-tiles** (`autoTileIfUntouched`, ≤4 windows) instead of cascading it 32px on top of the first, which made window mode look identical to the full-screen switcher. It stops as soon as the user moves/resizes/maximizes/snaps anything (`g.user`), so a hand-made layout is never rearranged.
  - **▦ Tidy** (taskbar, window mode only) tiles every non-minimized window in one tap via `VibeWin.tileGrid`: 2 → exact left/right halves (**stacked** on a portrait frame — side by side there gives two ~320px slivers pinned at `MINW`), 3 → two-over-one, 4 → quadrants, each inset by an 8px gutter so resize grips never sit at the extreme frame edge.
  - **Nothing overlaying the app area may be pointer-interactive in window mode** — `body.wm .vibe-coach { pointer-events:none }` (+ auto-hide). A coach banner renders at `bottom:60`, directly over the bottom edge and SE grip of a window, and stacks above it: the tip that says "drag an edge to resize" was eating the resize drag. This is the same class as the fixed-banner bug above and it has now bitten twice.
  - **Stacking/clamping invariants:** `#frames` carries `isolation:isolate` + `overflow:hidden` so a window's `z-index` (and the drag-mask's 99998) **cannot escape above the taskbar (100) or Start menu (110)**; a `ResizeObserver` on `#frames` re-clamps every window whenever the frame resizes for *any* reason. Title-bar buttons sit at `z-index:5`, **above** the resize handles (3–4), or the × becomes unclickable under the edge grip.
  - **Shell chrome above the app area MUST be in the flex flow, never `position:fixed`.** A fixed banner overlays `#frames` without resizing it, so the ResizeObserver can't see it and a window's title bar ends up *under* it — with the disk-warning banner up, a Tidy'd window's ×/▢/– all hit-tested to the banner and the window could not be closed, moved or maximized. `#sys-warn` is now a `flex:0 0 auto` first child of `<body>` like `.cu-strip`. Still overlay-positioned, and in this class if they grow: `#sys-keybar` (+ hint) and `.kbd-chip`. Full write-ups: `docs/design-decisions.md` §"Window mode: the chrome kept eating the window's own gestures" (v1.19.5–.9) and §"Window mode round 2 (v1.19.10)".
  - **Tests:** `landing/winmgr.test.js` (pure geometry) + `tests/e2e/tests/window-mode.spec.js` on the **tablet lanes** (`ipad-pro-11`, `ipad-pro-11-landscape`, `ipad-gen-11`). Window mode only ever runs on tablets/desktops, so a phone-only mobile lane cannot cover it — that gap is why v1.19.5–.9 were each found by hand.
- **Status bar** — live system stats (CPU% + temp, MEM used/total, GPU% + temp, VRAM used/total) that **ride the 5s desktop heartbeat** (the `system` field on `/api/desktop`, rendered by `renderSysStats` in `onDesktopResp`) rather than a standalone poll — one of the shell-tier polls **consolidated onto the heartbeat** (the taskbar stats and the Start-menu terminal-count badge, `terminals_running`, both folded in; the standalone `/api/system/status` + `/api/terminals/status` client loops were removed). Both are memoized server-side and collected **outside `_desktop_lock`**, so the fold doesn't lengthen the lock or duplicate work across clients. Rendered in a fixed-width CSS grid (`ch`-sized columns + `tabular-nums`) so labels don't shift sideways as values change digit-count. CPU temp from `k10temp` (Tctl), GPU temp from `amdgpu` (edge). When the GPU driver locks sysfs during heavy compute (EBUSY), util/temp/power **fall back to parsing `/sys/kernel/debug/dri/N/amdgpu_pm_info`** (manager already runs as root) so the numbers stay populated. The full 1/5/15-minute load average is shown only in the Monitor app's CPU card title. This readout is a **toggleable "System Stats" utility** (Start ▸ Utilities): when off, the CPU/GPU/MEM/VRAM block (and its taskbar separator) are hidden **and the server omits the `system` field** (so it isn't collected) — the taskbar space goes back to app tabs. The preference is **shared across all clients**: it lives on the desktop state (`sys_stats`) and is set via `POST /api/desktop/ui {sysStats}`, converging on every client within ~5s through the heartbeat (`applyServerSysStats` in `onDesktopResp`); `localStorage` is only a fast-load cache so there's no flash before the first heartbeat. (Deliberately **not** folded onto the heartbeat: the X11-window auto-surface poll — a `wmctrl` shell-out that could block — and the Services relay, which runs an `ss`/`/proc` scan only while the Services app is open; keeping conditional/heavier work off the heartbeat critical path is the point of consolidating *within* a tier rather than globally.) The **taskbar layout** keeps the tabs (`.task-apps { flex:1 1 auto; overflow-x:auto }`) growing to fill and scrolling when narrow, while the stats block, Start button, and Logout stay fixed-width (`flex-shrink:0`) — so a long tab list can never shove the stats off-screen or overlap them (the overlap bug that made the stats collide with the right-most tab).
- **System-health warning banner** — a full-width **red banner** at the top of the desktop for "something is wrong" alerts, a generic, extensible mechanism (not disk-specific). The manager's `_system_warnings()` returns a list of `{id, level:"warn"|"critical", text}` which rides the **desktop heartbeat** as the **`warnings`** field (always present, independent of the System-Stats toggle — a safety alert must show even with stats off) and `renderWarnings` in `onDesktopResp` paints one row per warning (`critical` a deeper red). **Adding a future warning = appending one block to `_system_warnings()`** (a wedged service, an overheating GPU, a failed backup…); each check must be a cheap syscall since it runs on the 5s heartbeat (memoized ~5s via `_cached("sys_warnings")`). The first producer is **disk-almost-full**: `os.statvfs("/")` → df-style Use%/free (both exclude the root reserve so they match the shell); **warn** at ≥90% or <10 GB free, **critical** at ≥95% or <2 GB free. This exists because a full root FS (from the *operator's own* workloads, not vibetop — vibetop's own state is ~1.6 MB) makes atomic state writes / terminals / saves fail in confusing, intermittent ways ("resize is broken", "keyboard weird") — the banner turns that into an obvious "you're out of disk". Dismissal (the row's ×) is **per `(id+level)` for the session** (`sessionStorage vibetop:warnsnooze`), so a cleared-then-returning warning re-shows next session and an **escalation** (warn→critical) re-surfaces immediately even if the milder one was dismissed; when the condition clears (empty `warnings`) the banner hides itself (`#sys-warn:empty { display:none }`). Thresholds are unit-tested (`test_metrics.py::test_system_warnings_thresholds`, monkeypatching `statvfs`).
- **Logout button** — taskbar far right (⏻ glyph). Clicking it does a full **fresh-start reset** then logs out: after a `vibeConfirm()` (the vibetop-styled modal — see the shared front-end modules note), it `POST`s `/api/reset` (stops every running terminal + its background processes, clears the saved desktop layout, drops in-memory office edit sessions, and resets the Browser to a blank Chromium) and only then navigates to `/cdn-cgi/access/logout`. The `href` stays as the no-JS fallback. Over the tunnel `/cdn-cgi/access/logout` is handled at Cloudflare's edge (its own signed-out page); on the **LAN** there's no Cloudflare in front so that path hits the origin — nginx serves a friendly `loggedout.html` via `location = /cdn-cgi/access/logout` (terminal site) instead of a 404.
- **PWA / installable** — `landing/manifest.json` (+ `apple-*` meta tags and an `apple-touch-icon` in `desktop.html`) makes "Add to Home Screen" launch the desktop **standalone**. Icons + a multi-size `favicon.ico` come from `landing/icons/generate-icons.py`.
  - **Service worker (`landing/sw.js`), deliberately conservative.** Navigations are **network-first with a 2.5s timeout** — so Cloudflare Access redirects still work (an expired session's redirect is passed through, never cached) while a *stalled* network falls back to the cached shell. Static sub-resources are cache-first/SWR. Everything live or auth-sensitive (`/api`, `/browser`, `/tN`, `/terminals`, `/files`, `/fileview`, `/cdn-cgi`) is **bypassed entirely**. Only pathnames in `SHELL_PAGES` are cacheable navigations, so any other HTML is network-only and can't go stale. Uses `skipWaiting()`+`clients.claim()`; `activate` deletes old caches; nginx serves `sw.js` `no-store`. **Bump `VERSION` in `sw.js` after a shell change** — that string is also the deploy signal below.
  - **Auto-refresh on deploy (push, not poll).** The manager's SSE stream `GET /api/events` watches the *deployed* `sw.js` VERSION and pushes a `reload` to every connected client the moment it changes (`X-Accel-Buffering: no` + ~18s pings keep it alive through nginx/Cloudflare with no nginx config). One reload refreshes the entire desktop including every app iframe, so a deploy reaches all of vibetop with no per-app update logic; persistent state survives (terminals/Browser reconnect, notes autosave, Files/Notes tabs are server-side). **Self-heal:** a reconnect whose `hello` reports a different version than the page loaded with also refreshes, so a tab that was asleep during the deploy isn't stranded. **The reload is a direct `window.location.reload()`, deliberately not `controllerchange`** — an *uncontrolled* page (`hadController=false`, e.g. after a hard reload) never fires that event, which silently ate the refresh. Rationale + the separate `hadController`-guarded handler for the browser's own background SW checks: `docs/design-decisions.md` §"Auto-refresh every client on deploy". Bootstrap: a client must already be on the auto-refresh build, so older open tabs need one manual reload.
  - **Tunnel gotcha:** icons/manifest sit behind Cloudflare Access, so a cookie-less favicon fetch gets the login page → no icon. Fix with an Access **Bypass** app for `/favicon.ico`, `/apple-touch-icon.png`, `/manifest.json`, `/icons/*` (`tunnel/README.md`). On iOS an installed PWA has its own cookie jar, so the first launch may need a one-time Access re-auth.
- Relays `/api/services/discover` to the Services app via `postMessage`, only while it's open — required for the Cloudflare tunnel where an iframe's own fetch doesn't carry the Access cookie, so the parent fetches and forwards. (Monitor fetches `/api/system/status` itself and uses no relayed data.)
- Listens for `postMessage` from the terminal app to open a clicked URL in the Browser app (launching Browser if it isn't already open). Also handles `open-files-at` (from the Upload app) to deep-link the Files app at a given path.
- **Mobile** — viewport meta is pinned (`user-scalable=no`) since iOS pinch-zoom is page-wide and once stuck can't be reliably reset; each app handles its own zoom internally (xpra zooms the canvas, Monitor and FileBrowser have their own responsive layouts). Body uses `100svh` so the taskbar stays in the always-visible region under the URL bar. The taskbar is horizontally scrollable when narrow, the Start menu spans the screen, and `monitor.html`'s 736px breakpoint collapses its two-column grid into a single scrollable column. xterm.js auto-focus is **suppressed on touch devices** so auto-switching into Terminal doesn't pop up the on-screen keyboard — the user taps the terminal to summon it. This has two sources: the desktop's `focus-terminal` `postMessage` (skipped on touch) **and ttyd's own focus when its WebSocket connects** (the one that fires on a fresh load — e.g. closing Browser auto-switches to a never-yet-loaded Terminal). The latter is caught by a guard injected into every `/tN/` page via the `sub_filter` in `terminal/install.sh`: on touch, it blurs any focus of the `.xterm-helper-textarea` unless it lands within 700ms of a real touch **inside the terminal page** (a genuine tap whitelists itself in the capture phase; the parent's close-× tap does not). A touch-only **system key bar** (`#sys-keybar`, rendered by `desktop.html` at the top when the keyboard is up — the soft keyboard lacks these) gives `esc`/`tab`/`^C`/arrows: each routes `{type:'kbd-key', key}` to the active app (Terminal → PTY bytes via `terminal-kbd.js`; Browser → xpra-patches). The **arrow keys double as a trackpad** — a tap sends that arrow once; press-and-**slide** (on any arrow) moves the cursor, distance-proportional (`HSTEP`/`VSTEP` px per step). The slide is **axis-locked** once movement passes 12px. Horizontal slides send **`Ctrl+F`/`Ctrl+B`** (emacs forward/backward-char, `KBD_KEY_BYTES.CtrlF`/`CtrlB` → `\x06`/`\x02`), **not** `→`/`←`: a TUI like Claude Code reuses the *arrows* for menu/history nav on an empty prompt, but Ctrl+F/B move the text cursor and are harmless no-ops when there's nothing to move. Vertical slides send `↑`/`↓` (no cursor-only equivalent; that axis is history/menu by nature). Touch capture lets the slide continue past the button edge. (This replaced a dedicated `⇆` pad key — folding it into the arrows saves a slot and reads naturally.) The bar lives at the top on purpose (iOS doesn't report the keyboard height to a nested-iframe input; the strip above the keyboard is unmeasurable), pinned to the visual-viewport bottom via `syncBar`.

## Utilities submenu

The **Services**, **Monitor**, **Claude Usage**, **Token Stats**, and **System Stats** features are grouped under a **"Utilities"** parent in the Start menu's **System** section — a **cascading flyout** (`#sm-util-parent` opens `.sm-sub` as a `position:fixed`, JS-placed panel **beside** the menu on desktop, or **overlaying** it as a "second page" when there's no side room; hover-opens on desktop, tap-toggles on touch). It's a flyout, not an inline expander, so opening it never grows the menu vertically. Each row has a Material 24-grid SVG icon in the same style/size as the app launchers (Claude Usage = gauge, Token Stats = trend-line, System Stats = memory chip; the Utilities parent = wrench). Claude Usage and System Stats are **toggle rows** (not apps — special-cased in the Start-menu click handler; the parent shows a `has-active` accent when either is on); **Monitor** and **Token Stats** are **normal apps** (iframes). Section membership is set by `section: 'utilities'` on the app's `APPS` entry (`buildStartMenu` routes by it, in `APPS`-key order). The three toggle/stat preferences are **shared across clients** (see the desktop-heartbeat notes above).


## Shell-wide front-end modules

**Coach tips (`landing/coach.js`)** — `window.vibeCoach(tips, opts)` holds the show-until-tapped state machine once, for every surface. Behavior: a tip **shows every time** its surface opens, has **no auto-hide**, and is dismissed by **tapping the banner itself** (no separate ×) — with a safety cap of **3** showings if never tapped. Using the gesture does *not* retire the tip. Only **one banner renders at a time**; `rotate:true` shows one tip per open so a surface with several gives each airtime. Tips live on four surfaces: **terminal** (rotating — two-finger-resize · tap-a-link→Browser · long-press→Copy, in `terminal-kbd.js`), **Files** (address-bar path jump), **Browser** (double-click/tap to re-fit · ⌨ to type), and the **Start menu** (cross-device ⏻ close, only when an app runs on another device). The Files/Browser/⏻ tips are **desktop-driven** (`coachForApp` in `desktop.html` fires them on app-activation / menu-open), so those iframes need no per-app tip code. `localStorage` keys are **versioned** (`vibetop:2fingerhint:v2`, `vibetop:kbdhint:v2`) — **to re-show a changed tip to users who dismissed the old one, bump the `:vN` suffix**. Host-wide kill switch: the Config app's *Feature hints* toggle (see `docs/apps.md` §Config app). Unit-tested in `landing/coach.test.js`.

**Shared front-end modules** — three dependency-free helpers are deployed to the web root (`landing/install.sh`), precached in `sw.js`, and guarded by `landing/js-syntax.test.js` (compile check). Two are included via `<script src>` across the app pages: `coach.js` (`window.vibeCoach`, the coach-tip state machine described above) and **`vibe-modal.js`** (`window.vibeConfirm(msg, opts)` / `vibeAlert(msg, opts)`, both returning a Promise). `vibe-modal.js` **replaces the native `window.confirm`/`alert`** — those render as off-brand OS dialogs (and appear sideways on a rotated tablet); the styled modal injects its own CSS on first use and renders inside the including document (so it covers the full-viewport app iframe it belongs to). `opts`: `{title, okText, cancelText, danger}`; `\n` line breaks honored. Used by the Logout confirm, Notes tab-close, Upload/Update/office-editor confirms. The third, **`apph.js`** (loaded only by `desktop.html`), fixes an **iOS standalone-PWA black band** after a Cloudflare Access login: after the cross-origin login, an installed PWA freezes the CSS unit `svh` *too short* (e.g. 753 on a 956px screen), so `body{height:100svh}` leaves a black band below the taskbar (a reload does NOT unfreeze it; only the first post-login session is bitten). In standalone mode `apph.js` drives `--app-h` from `max(visualViewport.height, documentElement.clientHeight)` (both measure the content area below the opaque status bar, so they can't overshoot like `100vh`/`lvh`), keeping the running MAX (reset on a width change = rotation) so the soft keyboard — which only shrinks the visual viewport — can't shrink the shell. Inert in regular Safari (`body` keeps `100svh`). Diagnostic overlay: `#vhdbg` or `localStorage.vhdbg='1'`.
