# Desktop shell (`shell/desktop.html`)

> The Start menu, taskbar, window mode, the 5s desktop heartbeat, PWA/service
> worker, warning banner, and mobile ergonomics. Apps hosted by this shell:
> `docs/apps.md`.

## The shell

The root page at `/` is a Windows-style shell:
- **Start button** — always present at the taskbar's left. Clicking it toggles the **Start menu**, a launcher listing seven everyday apps (Terminal, Browser, X11 Launcher, Files, Office, Notes, Upload), then a separated **System** subsection with the **Update** app (set apart since it's rarely used) and the **Utilities** flyout, each with icon + description. Picking one opens it. (This replaced the old always-pinned tab bar.) **Services** (in the Utilities flyout — Start ▸ Utilities ▸ Services) is an **auto-discovering network-service dashboard** (`apps/utilities/services/index.html`, served at `/landing.html`) — it lists the host's other web services (Ollama/Open WebUI, ThinLinc, Streamlit apps, Jupyter, …) with **zero config**. The manager's `GET /api/services/discover` (sibling module `terminal/service_discovery.py`) scans listening TCP sockets (`ss -tlnp`), keeps those bound to a **non-loopback** address (a process on `0.0.0.0`/`::` is a network service; loopback-only sockets — incl. all of vibetop's own internals — are excluded), drops infra ports/daemons (ssh/smtp/dns/rpc/db + vibetop's own `:80`), and **names each from its `/proc/<pid>/cmdline`** (a recognizer table for well-known apps → a port hint → `proc :port`; the *effective* program is pulled from the cmdline when the socket owner is a generic interpreter like `python3`, so `python3 …/vsmagent` is filtered and `python3 …/open-webui` is named "Open WebUI"). Each card's dot is green (it's listening); tapping a card opens the service in the **embedded Browser** (Chromium runs on the host, so it reaches the LAN service whether you're on the LAN or coming through the tunnel), with a `↗ new tab` link for LAN clients. Data comes from a direct `/api/services/discover` fetch (LAN) or a parent `postMessage` relay (tunnel). This replaced the old hand-maintained, gitignored `services.json` (which in practice stayed the shipped example — hence the rebuild). Result memoized ~5s server-side.
- **Taskbar apps** — only *opened* apps get a button (Windows-style), each with a close (×). Multiple apps can be open at once; the focused one is highlighted with a per-app accent underline. Buttons are **drag-reorderable** (HTML5 DnD — desktop only; it's a no-op on touch so tap/scroll are unaffected): dragover reshuffles the DOM live, dragend reads the new order back into `openApps` and persists it. App-switching is wired on **`pointerdown`** for mouse (close × and touch stay on `click`) for the same reason as the terminal tabs — a focused app iframe makes the browser eat the first taskbar click moving focus back to the parent, so click-based switching needed two clicks. The set of open apps, their order, and the active one are persisted **server-side** via `GET/POST /api/desktop` (file `~/.local/share/desktop-state.json`). **Windows are local to each instance** — opening an app on the phone does NOT open a window on the computer (window mirroring was tried and removed: the Browser is a single shared-size xpra display, so a wide desktop client connecting would force desktop layout onto the phone, and windows silently appearing is jarring). What *is* shared across instances: (1) the Start-menu **"running" dots show the UNION** of apps open on any live instance (awareness), (2) a **logout/reset clears every instance**, and (3) **close-on-all-devices** — a running app's Start-menu row shows a soft **⏻ power button** (only when running; a real tap-target, confirmed) that closes that app on *every* client (the one place an app open only on another device is reachable). Each browser has a stable `INSTANCE_ID` (localStorage); the manager keeps a **per-instance registry** (`{instances:{id:{open,active,ts}}, reset_epoch}`) — a 5s heartbeat (`pushDesktop`, plus a re-register on `visibilitychange`) keeps an instance in the "live" union (`DESKTOP_TTL` 120s — must exceed browsers' ~60s background-tab timer throttling or an idle machine's dots wrongly go dark elsewhere), and the same id lets a device **restore its own windows** (`GET /api/desktop?instance=`) on reload, not the other device's. Closing via the taskbar × is local (drops from this instance's set; the dot goes dark once no live instance has it). To close across devices, the Start-menu ✕ calls `POST /api/desktop/close {app}`, which records the **live instances that currently have the app open** in `close_targets` (`{appId:[instanceId,…]}`); each instance closes the app when it sees its own id listed in a heartbeat reply, then reports an open-set without it and the server prunes it out (also pruned when an instance goes stale). Targeting by instance id (not a global flag/counter) means **reloading the holding device still closes it**, and a stuck holder can't poison the app for other devices. `/api/reset` bumps `reset_epoch`; every other instance sees it advance on its next heartbeat and tears its own desktop down (`clearAllLocal`). On a fresh desktop with nothing open the Start menu auto-opens.
- **App frames** — each app is an iframe (full-viewport by default; a floating window in **Window mode**, below), **created** on first open but only `src`-loaded on first activation (`loadIfNeeded`) so the inner content always measures the real viewport (otherwise xterm.js / FitAddon initialise at 0×0 and the terminal renders truncated) — **except in window mode, where `renderWindows()` loads every window it shows** (a visible window has real dimensions; before v1.19.59 only the focused window loaded, so a reload restored every other window as a black src-less iframe). Closed apps are **removed from the DOM** (true unload). All iframes carry `allow="clipboard-read; clipboard-write"` for cross-iframe clipboard.
- **Games** (v1.19.70, Start ▸ Games) — Minesweeper, Klondike Solitaire, and 2048 as ordinary desktop apps: each a fully self-contained page (`apps/games/minesweeper/minesweeper.html`, `solitaire.html`, `game2048.html` — inline CSS/JS, no external resources, vibetop palette), registered in `APPS` with `section:'games'` and grouped under a **Games flyout** (v1.19.72 — same mechanism as Utilities: the side-flyout/drill-down wiring is now a `makeFlyout` factory, one instance per parent, opening one closes the others) so they get windows/taskbar/running-dots/⏻ for free. Touch-first (long-press flag with reveal suppression, pointer-event card drag + tap-to-move fallback, swipe), responsive from ~320px floating windows to full-screen. Loaded on demand — deliberately not in the sw precache. Covered by `tests/e2e/tests/games.spec.js` and auto-covered by the page-inline-script parse guard in `shell/js-syntax.test.js`.
- **Per-game leaderboards** (v1.19.160) — each game has **its own**, and it is part of that game, not a separate app: a 🏆 card that opens over that game's own board from its 🏆 toolbar button or the 🏆 Leaderboard button on its game-over card, styled and sized exactly like that game's How-to-play card (`.overlay.help`, `z-index: 7` so it wins whichever opens second; Escape closes it first; 2048 blocks arrows behind it and Circuit Runner pauses the run, the same as its help card). Each shows a top-10 plus the stats that mean something for THAT game — Minesweeper played/won/win-rate/current+best streak **per difficulty** with its own difficulty pills, Solitaire deals/solved/win-rate/streak, 2048 best tile + times it reached 2048, Circuit runs/furthest sector/cleared — and a Reset behind `vibeConfirm`. The shared part is only what would otherwise be pasted four times: `shared/gamescore.js` (`window.vibeScores`) holds a per-game `SPEC` table, `panel()` to draw stats + list, `record`/`list`/`render` for the top-3 teaser on the game-over cards, and `finish`/`stats`/`reset`/`seedOf`. Stored per browser in `vibetop:scores:<game>` / `vibetop:stats:<game>` — no server side, no cross-user ranking.
- **Circuit Runner** (v1.19.141, Start ▸ Games ▸ 🤖 — `apps/games/circuit/circuit.html`) — a side-scrolling platformer in the SMB tradition, self-contained like the others: sprites are pixel arrays baked into offscreen canvases at load, the world is a 16px tile grid, and sound is synthesised with WebAudio (no images, no audio files, no libraries). Physics runs at a fixed 60Hz in per-frame pixel units — NOT delta-timed, because the feel (skid, momentum-carrying jumps, the exact height of a full jump) lives in those constants and drifts if you scale them by a variable dt. Five sectors (surface / tunnels / **coolant** / uplink towers / the core), small→big→fire suits, star power, goombas, koopas and their shells, paratroopas, piranha plants, bullet bills, podoboos, firebars, cheep-cheeps, bloopers, moving platforms, springboards, breakable bricks, ?-blocks, a **beanstalk to coin heaven**, a warp pipe to a bonus room, a flagpole (with fireworks when the clock ends in 1/3/6) and a bridge-cutting axe. Water is per-TILE, not per-level — swimming starts when the tile at your chest is water, so the flag at the end of 1-3 sits on dry seabed you walk out onto, and any level can flood a section. Underwater, jump is one stroke per press (holding does nothing) and nothing can be stomped. Keyboard, on-screen pad (touch only), and gamepad. Renders taller than 240px on a tall window and fills the extra with solid earth, so a phone in portrait shows ground rather than a black band.
  - **Testing a canvas game**: the DOM says nothing, so the page exposes read-only hooks — `__cr()` (state snapshot), `__crBuild(i)` (a level's tile grid), `__crTest.place()` (set up a situation instead of playing into it), `__crSpriteWarnings` (any pixel row that is not its declared width). `tests/e2e/tests/circuit.spec.js` uses them for a **level solvability audit**: it walks the footholds from start to flag and fails if any hop is further than a running jump. That audit caught a sector shipping with a 9-tile gap and a warp pipe into a bonus room built past the level width (which `Level.set` silently discards) — neither is visible by reading the builder.
- **Iron Frontier** (Start ▸ Games ▸ ⚔️ — `apps/games/rts/rts.html`) — an isometric real-time-strategy skirmish against a single AI opponent, self-contained like the others. **Two asymmetric factions**, picked on the menu card (the AI always takes the other): the **Directorate** trades armour for reach and speed — Lancers outrange, Spectres see half the map and hunt harvesters, Sentry Guns shred infantry — while the **Collective** trades finesse for mass — Conscripts are nearly free, Mammoths absorb punishment and splash, Tesla Coils hit vehicles hard and eat power. Harvesters, Rocketeers and the five core structures are shared. Rosters are DATA, not special cases: each `UNITS`/`BLDS` entry carries a `fac` (null = shared) that `canBuild()` enforces, the build panel lists only your own, and the AI builds its own faction's kit. Ore economy: harvesters mine and haul to refineries for credits, and ore patches run dry, so the map's contested middle is worth taking. A power grid throttles production and darkens defences when short. Structures are queued and then placed by hand anywhere within a **6-tile build radius** of your own buildings — the legal area is washed green while placing, so it is visible rather than found by trial. Extra Barracks or War Factories speed their own queue (RA2's MultipleFactory=0.8: cumulative, capped at six) and act as extra exits, since `producerFor()` round-robins. Production buildings take a **rally point** whose line follows the real A* route and flags the destination; an unreachable one draws red and says so. Units path with A*, are ordered with box-select + right-click, group with Ctrl+1-5, and there is a minimap. **Space** (or H) jumps back to base, **P** pauses (a click anywhere resumes), **Esc** cancels placing; losing focus does NOT pause, because a real-time match should not stop when the cursor wanders off. Edge scrolling is a 44px zone with a squared speed curve and no dwell timer — the way C&C does it — and a pointer travelling fast across it is ignored, so going to the command bar and back never drags the map. The AI is layered — strategy, production, tactics, per-frame micro — commits attacks as waves and pulls survivors back when one fails, scouts and withdraws the scout, and counters what it has actually SEEN. It expands **production** the way a human does: a saturated build lane plus a fat bank buys another War Factory or Barracks (up to three each), so it uses the same multi-building speed-up you do rather than sitting on credits it cannot spend — the absence of that rule was worth a 90/10 faction skew on its own. If a finished structure has nowhere legal to go it is eventually cancelled and refunded, because a building stuck "ready" blocks every later structure. Its three difficulties differ only by handicaps on **its own** play: reaction time, orders per pass, focus fire, wave size, and how long it grants you before the first attack. It gets no free credits and no vision it hasn't scouted — the difficulty knob is discipline, not omniscience. Desktop only; a touch device gets a notice card. Covered by `apps/games/rts/rts.test.js` (content and balance audits; the headless AI-vs-AI matches are an opt-in `RTS_SLOW=1` tier so the pre-commit hook stays fast — see `docs/testing.md`) and `tests/e2e/tests/rts.spec.js`, driven through the page's `window.__rts*` hooks the same way Circuit Runner is driven through `window.__cr*` (see below).
- **Wallpaper widgets** (v1.19.62) — a glanceable cluster in the desktop background's top-right corner (hidden ≤736px — the taskbar clock covers phones): a large **device-local clock + long date** sharing the taskbar clock's minute-boundary tick, the **current-month calendar** (rebuilt only on a day change; today carries the app accent), and a small **host line** (`hostname · up Nd Nh`) riding the heartbeat's `system` field — it appears only while System Stats is on (`.wp-host:empty` hides it). Lives inside `.wallpaper` (pointer-events:none, painted over by any active app).
- **Window mode (v1.19.x) — floating, movable, resizable windows; OPT-IN, default OFF.** The default desktop is still the classic full-screen one-app-at-a-time switcher (v1.19.0 shipped windows default-on; **v1.19.2 reverted that on purpose**). Turn it on with the **windows button in the taskbar** (two overlapping window outlines, inline SVG on `currentColor` so the lit state recolors it; it was the 🗔 emoji until v1.19.55) (beside Start, one tap, applied live) — **its only surface, there is deliberately no Start-menu row** — or with **`?wm=1`** / `?wm=0`, which **stick** (persisted, so it's a one-time switch, not a per-visit flag). **The label is "Floating windows"** — it names what turns on rather than a mode. ("Stage Manager" was considered and rejected: that names Apple's thumbnail-rail paradigm, which this is not.) **One surface, and it took three tries to land on it** (full history in design-decisions): buried in the Utilities flyout → couldn't be found; flyout **plus** button → the same switch in two places, reported as "two window control buttons"; menu-row only → removed the wrong one. Now: the 🗔 button and nothing else. `body.wm-capable` gates its visibility (`windowModeCapable()`, split out of `windowModeOn()`), so it shows wherever the mode is *available* — on **or** off, since a switch you can only find once it is on is no switch. Lit = on; the `title` carries the explanation the menu row used to give. **It is the ONLY icon** — a separate ▦ Tidy button sat beside it until v1.19.44, when "the functionality can totally be satisfied with one icon" retired it: **turning windows ON always re-tiles into an even split**, so resetting a messy layout is tap-off, tap-on. That call runs after `renderWindows()` (tileGrid measures the live `frameBox()`) and deliberately ignores the user-arranged guard `autoTileIfUntouched` respects — tapping the switch IS the request to re-tile. Accepted cost: a hand-made layout does not survive an off/on cycle.
  - **It is device-local** — `localStorage['vibetop:wm']` for the flag, `localStorage['vibetop:wins']` for per-app geometry. This is the odd one out among the shell toggles: **System Stats and Claude Usage are shared across clients** via `POST /api/desktop/ui` + the heartbeat, but window mode and window geometry are **not** synced and have no server field. That's deliberate and matches "windows are local to each instance" above — a phone and a 4K desktop want different layouts.
  - **Gated by screen SIZE, not touch** (`windowModeOn`), on **both** sides: `min(w,h) >= 600 && max(w,h) >= 900`, plus a fine-pointer arm (`w >= 900 && pointer:fine`) so a short, wide desktop window keeps windows. Tablets/iPads get windows in **both orientations**; phones never do. A long-side-only test cannot work — Pixel 9 Pro landscape is 900×375 — and the old `max >= 1000 || w >= 900` missed the 656×944 iPad gen 11 in portrait, so windows vanished when that iPad was rotated (v1.19.10). Touch drag/resize works via enlarged grips + `touch-action:none` under `body.is-touch`.
  - **Structure, load-bearing:** each iframe is wrapped **once** in a `.win` container and **never reparented**, so xpra/terminal state and the deferred-`src` 0×0 fix survive. The explicit height chain `.win{inset:0}` → `.win-body{flex:1}` → `iframe{height:100%}` matters: a replaced `<iframe>` with `height:auto` collapses to its intrinsic ~150px — the exact bug that killed an earlier tiling attempt. Default/mobile render the **same DOM** as a chromeless full-bleed window (verified pixel-identical), so there is one code path, not two.
  - **Pure geometry lives in `shell/winmgr.js`** (`window.VibeWin`; DOM-free like `terminal/lib/tab-sync.js`, unit-tested by `winmgr.test.js`): `clampGeom`, `resizeGeom` (per-direction), `defaultGeom` (cascade), snap, `tileGrid`. `desktop.html` does only the DOM/pointer glue — **keep new geometry decisions in `winmgr.js`** where they're testable.
  - **Gestures:** **click anywhere in a window** to focus + raise it (the parent listens on each same-origin frame's `contentDocument` — iframe events don't bubble, so before v1.19.10 only the title bar, the 5px edges and the taskbar raised a window); drag the title bar to move; drag any of 8 edges/corners to resize (visible diagonal SE grip, v1.19.4); **▢** or **double-tap the title bar** to maximize/restore (▢ becomes **❐ "Restore"** while maximized); **–** to minimize; drag to a side edge (28px mouse / 48px touch) to snap to a half. Edge-snap is **halves only** — top-edge snap-to-maximize was removed (▢ already does it). The double-tap is detected from two `pointerdown`s (<400ms, <24px), not `dblclick` — but **decided on pointerUP**, only if the gesture moved <10px, or "tap the title bar, then drag" maximizes instead of moving.
  - **The title-bar buttons act on `pointerdown`+`pointerup`, NOT `click`** — they carry `tabindex` for keyboard access, which makes WebKit focus the span on pointerdown, and `setActive()` then moves focus into the app iframe mid-gesture so **WebKit dispatches no `click` at all**. Measured on iPad; don't move them back. Enter/Space work via a `keydown` handler.
  - **Taskbar semantics in window mode:** a minimized window's button is dimmed (`.task-app.minimized`), clicking the focused app's button minimizes it, and clicking a minimized one restores it (`taskbarToggle`) — in the classic desktop `setActive(null)` *is* minimizing, but with every window visible that only dropped the focus highlight.
  - **Snap layouts — hover the taskbar 🗔** (mouse, 420ms hover-intent) or **long-press** it (touch, 500ms): a palette opens above the bar offering **Halves / Thirds / 1 + 2 / Stacked / Quarters**, sized 131×85 per tile (176×112 on touch; the row wraps and is capped at `min(92vw,760px)` so it can never run off a narrow frame) with a `.wl-hint` caption reading **"(drag to switch)"** — on touch, "(hold an icon, then tap another to switch)". The caption exists because the drag affordance is otherwise invisible; the tiles sit in a `.wl-row` so the hint can sit under them. Click a tile and **every** window is arranged — the focused one takes zone 0 (the main zone), the rest follow in taskbar order, overflow minimized (same rule as `tidyWindows`, same reason: overlapping tiles put one window's ×/▢/– on top of its neighbour's). **Each zone in a tile previews the app icon of the window that will land there** (so "which one gets the big zone in 1 + 2?" is answered before anything is clicked), and the palette is a **staging area** (user-requested compose-then-commit): **a tile click selects** (accent ring — nothing moves), **dragging an icon from one zone onto another swaps those two occupants on the board** (touch: **long-press picks a zone up, tap another swaps**; a moving finger cancels), swaps compose freely in one visit, and the **Apply** button in the palette footer commits the selected board — dismissing (outside click / mouse-away while pristine) discards with nothing moved, so exploration is free. Once anything is selected or staged the hover auto-hide is suspended (a stray mouse-leave must not discard a composition); Apply is disabled until a tile is selected. Clicks deliberately do NOT rearrange (zones cover the whole tile — a selection click that also staged a swap would mutate the board by accident), which also retires the old zone-click steering and its hover preview. **The opening board is derived, never stored**: when the open windows already sit exactly in a layout's zones, that tile shows who is where NOW and opens pre-selected (`VibeWin.zoneOccupancy` — so Apply with no edits is a visible no-op and swaps compose across commits), otherwise the default rule applies (focused → zone 0, rest in taskbar order, `VibeWin.zoneAssign`). Boards and placement share these pure functions plus `VibeWin.swapZones` — `applyLayout(key, assign)` commits the exact board the tile shows — so the board cannot lie. **It hung off a window's ▢ in v1.19.45 and that was the wrong home** — the palette arranges everything, so a control on window A silently moved B and C ("all windows can be controlled from another window"). v1.19.46 moved it to the desktop-level control; **▢ is plain maximize again**. Tapping 🗔 still toggles (a `held` flag stops a long-press release from also toggling). It also **removes any coach banner** on open: those render at `bottom:60` with `z-index 2147483000`, directly over the palette — click-through in window mode, but they hid it. Layouts are `VibeWin.LAYOUTS` — **fractions**, so they survive resize and rotation — and `layoutsFor(box, n)` offers only those that FIT at `MINW`/`MINH` and whose zone count **equals** the number of open windows. **Exactly equals, not merely "not more"** — the first cut only excluded layouts with too many zones, so three open windows were still offered Halves and Stacked, and picking one silently minimized the third. A count with no matching layout (1, or 5+) offers nothing and the palette stays shut; the even split from toggling the mode off and on covers those. **`layoutGeoms` rounds EDGES, never sizes**: rounding each width independently made thirds of 1400px into three 467px zones that overlapped by a pixel — caught by `winmgr.test.js`, which asserts the zones tile the box exactly.
  - **Opening a 2nd app auto-tiles** (`autoTileIfUntouched`, ≤4 windows) instead of cascading it 32px on top of the first, which made window mode look identical to the full-screen switcher. It stops as soon as the user moves/resizes/maximizes/snaps anything (`g.user`), so a hand-made layout is never rearranged.
  - **`tidyWindows()`** — reached by turning the 🗔 toggle ON (no button of its own since v1.19.44) — tiles every non-minimized window via `VibeWin.tileGrid`: 2 → exact left/right halves (**stacked** on a portrait frame — side by side there gives two ~320px slivers pinned at `MINW`), **3 → three even columns** (was two-over-one until v1.19.45: `ceil(sqrt(3))`=2 columns makes the odd window out twice the area of its neighbours — "really ugly"; portrait stacks, and a frame under `3*MINW` falls back to 2 columns), 4 → quadrants, each inset by an 8px gutter so resize grips never sit at the extreme frame edge.
  - **Resizing works from all 8 edges/corners, and the cursor is the affordance.** `.win-rz-{n,s,e,w,ne,nw,se,sw}` — edges reaching **10px outside → 8px inside** the frame, corners **26px** (12/38px on touch), each with its own resize cursor — **`col-resize`/`row-resize` on the straight edges, in EVERY browser on purpose**: `ew-/ns-resize` draw the same bare ↔/↕ the OS uses on the host window's own edges, so you cannot tell which window you are about to resize ("on Windows Chrome the two are the same, hard to tell"); col-/row-resize add the bar through the arrows. It began as a macOS-Safari-only mapping workaround — see design-decisions — and the distinguishability was the accident worth keeping. Corners keep the axis keywords and still collide with the host's diagonal; only an image cursor could separate them; the visible SE hatch is the FALLBACK affordance, kept only where the cursor cannot speak — touch (no hover) and WebKit (macOS Safari draws no diagonal cursor at all); it is retired on mouse-driven Chrome/Firefox via `@supports not (background: -webkit-named-image(i))` + `(pointer: fine)`. Two things were wrong and are now tested together in `window-mode.spec.js`: 5px edges made it *feel* like the SE corner was the only grab point, and **the NE corner was genuinely dead** — the `×` is `z-index:5`, the handles are 3–4, so the button won the 9×9 square they overlapped (that z-index is itself the fix for an earlier "× stole the tap" bug, so the two constraints must be solved together, not traded). Fix: **inset the controls from the frame edge** — `.win-titlebar { padding-right: 18px }` (28px on touch) so no control can sit inside the corner grab zone, exactly as a real window frame insets its buttons. **The ring reaches OUTSIDE the window on purpose**: Tidy insets each tile by `GAP=8`, so two side-by-side tiles have a **16px gutter** that belonged to neither window — grabbing the divider (the obvious gesture) hit bare `#frames`. That is why *"cannot resize from left or right"* while top/bottom felt fine: a side-by-side split only puts a gutter on the vertical edges. Two 10px outside rings now meet inside it (10 and not 8 because the window's 1px border eats one on each side — 8 left a literal one-pixel dead seam mid-gutter). This requires `.win.floating` to **not** set `overflow:hidden` (it clipped its own children); the rounded-corner clip moved to `.win-titlebar` (`7px 7px 0 0`) and `.win-body` (`0 0 7px 7px`). **Two invariants: `title-bar padding-right > corner inside-reach (size − outside)`, and the outside reach must exceed half the tile gutter.** The **`#win-dragmask`** (which covers every iframe during a gesture so the pointer stream survives crossing one) **must carry the gesture's cursor** — set per-drag in `setupWM` — and reset it to `default` before it disappears. Window chrome → app-iframe transitions also pulse an explicit default cursor for one frame; without those handoffs Chromium can keep painting `row-resize`/`col-resize` after the pointer has already left the narrow handle. Unset on press replaced the resize cursor with an arrow during the drag; left set on release stranded the resize cursor over app content.
  - **Nothing overlaying the app area may be pointer-interactive in window mode** — `body.wm .vibe-coach { pointer-events:none }` (+ auto-hide). A coach banner renders at `bottom:60`, directly over the bottom edge and SE grip of a window, and stacks above it: the tip that says "drag an edge to resize" was eating the resize drag. This is the same class as the fixed-banner bug above and it has now bitten twice.
  - **Stacking/clamping invariants:** `#frames` carries `isolation:isolate` + `overflow:hidden` so a window's `z-index` (and the drag-mask's 99998) **cannot escape above the taskbar (100) or Start menu (110)**; a `ResizeObserver` on `#frames` re-clamps every window whenever the frame resizes for *any* reason. Title-bar buttons sit at `z-index:5`, **above** the resize handles (3–4), or the × becomes unclickable under the edge grip.
  - **Shell chrome above the app area MUST be in the flex flow, never `position:fixed`.** A fixed banner overlays `#frames` without resizing it, so the ResizeObserver can't see it and a window's title bar ends up *under* it — with the disk-warning banner up, a Tidy'd window's ×/▢/– all hit-tested to the banner and the window could not be closed, moved or maximized. `#sys-warn` is now a `flex:0 0 auto` first child of `<body>` like `.cu-strip`. Still overlay-positioned, and in this class if they grow: `#sys-keybar` (+ hint) and `.kbd-chip`. Full write-ups: `docs/design-decisions.md` §"Window mode: the chrome kept eating the window's own gestures" (v1.19.5–.9) and §"Window mode round 2 (v1.19.10)".
  - **Tests:** `shell/winmgr.test.js` (pure geometry) + `tests/e2e/tests/window-mode.spec.js` on the **tablet lanes** (`ipad-pro-11`, `ipad-pro-11-landscape`, `ipad-gen-11`). Window mode only ever runs on tablets/desktops, so a phone-only mobile lane cannot cover it — that gap is why v1.19.5–.9 were each found by hand.
- **Status bar** — live system stats (CPU% + temp, MEM used/total, GPU% + temp, VRAM used/total) that **ride the 5s desktop heartbeat** (the `system` field on `/api/desktop`, rendered by `renderSysStats` in `onDesktopResp`) rather than a standalone poll — one of the shell-tier polls **consolidated onto the heartbeat** (the taskbar stats and the Start-menu terminal-count badge, `terminals_running`, both folded in; the standalone `/api/system/status` + `/api/terminals/status` client loops were removed). Both are memoized server-side and collected **outside `_desktop_lock`**, so the fold doesn't lengthen the lock or duplicate work across clients. Rendered in a fixed-width CSS grid (`ch`-sized columns + `tabular-nums`) so labels don't shift sideways as values change digit-count. CPU temp from `k10temp` (Tctl), GPU temp from `amdgpu` (edge). When the GPU driver locks sysfs during heavy compute (EBUSY), util/temp/power **fall back to parsing `/sys/kernel/debug/dri/N/amdgpu_pm_info`** (manager already runs as root) so the numbers stay populated. The full 1/5/15-minute load average is shown only in the Monitor app's CPU card title. This readout is a **toggleable "System Stats" utility** (Start ▸ Utilities): when off, the CPU/GPU/MEM/VRAM block (and its taskbar separator) are hidden **and the server omits the `system` field** (so it isn't collected) — the taskbar space goes back to app tabs. The preference is **shared across all clients**: it lives on the desktop state (`sys_stats`) and is set via `POST /api/desktop/ui {sysStats}`, converging on every client within ~5s through the heartbeat (`applyServerSysStats` in `onDesktopResp`); `localStorage` is only a fast-load cache so there's no flash before the first heartbeat. (Deliberately **not** folded onto the heartbeat: the X11-window auto-surface poll — a `wmctrl` shell-out that could block — and the Services relay, which runs an `ss`/`/proc` scan only while the Services app is open; keeping conditional/heavier work off the heartbeat critical path is the point of consolidating *within* a tier rather than globally.) The **taskbar layout** keeps the tabs (`.task-apps { flex:1 1 auto; overflow-x:auto }`) growing to fill and scrolling when narrow, while the stats block, Start button, and Logout stay fixed-width (`flex-shrink:0`) — so a long tab list can never shove the stats off-screen or overlap them (the overlap bug that made the stats collide with the right-most tab).
- **System-health warning banner** — a full-width **red banner** at the top of the desktop for "something is wrong" alerts, a generic, extensible mechanism (not disk-specific). The manager's `_system_warnings()` returns a list of `{id, level:"warn"|"critical", text}` which rides the **desktop heartbeat** as the **`warnings`** field (always present, independent of the System-Stats toggle — a safety alert must show even with stats off) and `renderWarnings` in `onDesktopResp` paints one row per warning (`critical` a deeper red). **Adding a future warning = appending one block to `_system_warnings()`** (a wedged service, an overheating GPU, a failed backup…); each check must be a cheap syscall since it runs on the 5s heartbeat (memoized ~5s via `_cached("sys_warnings")`). The first producer is **disk-almost-full**: `os.statvfs("/")` → df-style Use%/free (both exclude the root reserve so they match the shell); **warn** at ≥90% or <10 GB free, **critical** at ≥95% or <2 GB free. This exists because a full root FS (from the *operator's own* workloads, not vibetop — vibetop's own state is ~1.6 MB) makes atomic state writes / terminals / saves fail in confusing, intermittent ways ("resize is broken", "keyboard weird") — the banner turns that into an obvious "you're out of disk". Dismissal (the row's ×) is **per `(id+level)` for the session** (`sessionStorage vibetop:warnsnooze`), so a cleared-then-returning warning re-shows next session and an **escalation** (warn→critical) re-surfaces immediately even if the milder one was dismissed; when the condition clears (empty `warnings`) the banner hides itself (`#sys-warn:empty { display:none }`). Thresholds are unit-tested (`test_metrics.py::test_system_warnings_thresholds`, monkeypatching `statvfs`).
- **Logout button** — taskbar far right (⏻ glyph). Clicking it does a full **fresh-start reset** then logs out: after a `vibeConfirm()` (the vibetop-styled modal — see the shared front-end modules note), it `POST`s `/api/reset` (stops every running terminal + its background processes, clears the saved desktop layout, drops in-memory office edit sessions, and resets the Browser to a blank Chromium) and only then navigates to `/cdn-cgi/access/logout`. The `href` stays as the no-JS fallback. Over the tunnel `/cdn-cgi/access/logout` is handled at Cloudflare's edge (its own signed-out page); on the **LAN** there's no Cloudflare in front so that path hits the origin — nginx serves a friendly `loggedout.html` via `location = /cdn-cgi/access/logout` (terminal site) instead of a 404.
- **PWA / installable** — `shell/manifest.json` (+ `apple-*` meta tags and an `apple-touch-icon` in `desktop.html`) makes "Add to Home Screen" launch the desktop **standalone**. Icons + a multi-size `favicon.ico` come from `shell/icons/generate-icons.py`.
  - **Service worker (`shell/sw.js`), deliberately conservative.** Navigations are **network-first with a 2.5s timeout** — so Cloudflare Access redirects still work (an expired session's redirect is passed through, never cached) while a *stalled* network falls back to the cached shell. Static sub-resources are cache-first/SWR. Everything live or auth-sensitive (`/api`, `/browser`, `/tN`, `/terminals`, `/files`, `/fileview`, `/cdn-cgi`) is **bypassed entirely**. Only pathnames in `SHELL_PAGES` are cacheable navigations, so any other HTML is network-only and can't go stale. Uses `skipWaiting()`+`clients.claim()`; `activate` deletes old caches; nginx serves `sw.js` `no-store`. **Bump `VERSION` in `sw.js` after a shell change** — that string is also the deploy signal below.
  - **Auto-refresh on deploy (push, not poll).** The manager's SSE stream `GET /api/events` watches the *deployed* `sw.js` VERSION and pushes a `reload` to every connected client the moment it changes (`X-Accel-Buffering: no` + ~18s pings keep it alive through nginx/Cloudflare with no nginx config). One reload refreshes the entire desktop including every app iframe, so a deploy reaches all of vibetop with no per-app update logic; persistent state survives (terminals/Browser reconnect, notes autosave, Files/Notes tabs are server-side). **Self-heal:** a reconnect whose `hello` reports a different version than the page loaded with also refreshes, so a tab that was asleep during the deploy isn't stranded. **The reload is a direct `window.location.reload()`, deliberately not `controllerchange`** — an *uncontrolled* page (`hadController=false`, e.g. after a hard reload) never fires that event, which silently ate the refresh. Rationale + the separate `hadController`-guarded handler for the browser's own background SW checks: `docs/design-decisions.md` §"Auto-refresh every client on deploy". Bootstrap: a client must already be on the auto-refresh build, so older open tabs need one manual reload.
  - **Tunnel gotcha:** icons/manifest sit behind Cloudflare Access, so a cookie-less favicon fetch gets the login page → no icon. Fix with an Access **Bypass** app for `/favicon.ico`, `/apple-touch-icon.png`, `/manifest.json`, `/icons/*` (`tunnel/README.md`). On iOS an installed PWA has its own cookie jar, so the first launch may need a one-time Access re-auth.
- Relays `/api/services/discover` to the Services app via `postMessage`, only while it's open — required for the Cloudflare tunnel where an iframe's own fetch doesn't carry the Access cookie, so the parent fetches and forwards. (Monitor fetches `/api/system/status` itself and uses no relayed data.)
- Listens for `postMessage` from the terminal app to open a clicked URL in the Browser app (launching Browser if it isn't already open). Also handles `open-files-at` (from the Upload app) to deep-link the Files app at a given path.
- **Mobile** — viewport meta is pinned (`user-scalable=no`) since iOS pinch-zoom is page-wide and once stuck can't be reliably reset; each app handles its own zoom internally (xpra zooms the canvas, Monitor and FileBrowser have their own responsive layouts). Body uses `100svh` so the taskbar stays in the always-visible region under the URL bar. The taskbar is horizontally scrollable when narrow, the Start menu spans the screen, and `monitor.html`'s 736px breakpoint collapses its two-column grid into a single scrollable column. xterm.js auto-focus is **suppressed on touch devices** so auto-switching into Terminal doesn't pop up the on-screen keyboard — the user taps the terminal to summon it. This has two sources: the desktop's `focus-terminal` `postMessage` (skipped on touch) **and ttyd's own focus when its WebSocket connects** (the one that fires on a fresh load — e.g. closing Browser auto-switches to a never-yet-loaded Terminal). The latter is caught by a guard injected into every `/tN/` page via the `sub_filter` in `terminal/install.sh`: on touch, it blurs any focus of the `.xterm-helper-textarea` unless it lands within 700ms of a real touch **inside the terminal page** (a genuine tap whitelists itself in the capture phase; the parent's close-× tap does not). A touch-only **system key bar** (`#sys-keybar`, rendered by `desktop.html` at the top when the keyboard is up — the soft keyboard lacks these) gives `esc`/`tab`/`^C`/arrows: each routes `{type:'kbd-key', key}` to the active app (Terminal → PTY bytes via `terminal-kbd.js`; Browser → xpra-patches). The **arrow keys double as a trackpad** — a tap sends that arrow once; press-and-**slide** (on any arrow) moves the cursor, distance-proportional (`HSTEP`/`VSTEP` px per step). The slide is **axis-locked** once movement passes 12px. Horizontal slides send **`Ctrl+F`/`Ctrl+B`** (emacs forward/backward-char, `KBD_KEY_BYTES.CtrlF`/`CtrlB` → `\x06`/`\x02`), **not** `→`/`←`: a TUI like Claude Code reuses the *arrows* for menu/history nav on an empty prompt, but Ctrl+F/B move the text cursor and are harmless no-ops when there's nothing to move. Vertical slides send `↑`/`↓` (no cursor-only equivalent; that axis is history/menu by nature). Touch capture lets the slide continue past the button edge. (This replaced a dedicated `⇆` pad key — folding it into the arrows saves a slot and reads naturally.) The bar is pinned just above the keyboard at `vvBottom - BAR_H` via `syncBar` (an earlier revision put it at the top of the screen; that note is superseded). **The desktop also applies the keyboard "lift" itself, from the same reading, in the same turn** (`VibeKeybar.compute` in `shell/keybar.js`, unit-tested against the viewport states field-recorded on the reporting iPhone): lift = `min(frame bottom, last non-blank terminal row + 4px) − bar top`, clamped ≥ 0, applied as a `translateY` on `terminals.html`'s `.frames` container via the same-origin frame chain (the last-non-blank row is read the same way: desktop → `terminals.html __activeTermFrame()` → `/tN/ window.term`; it is stable across TUI repaints, unlike `cursorY`, and a short decaying max bridges transient blank frames). **Only the desktop can see any of this**: a nested iframe's `visualViewport` does NOT shrink for the soft keyboard. Because the lift sits on the shared container, *all* terminal tabs are corrected at once (no per-tab scroll state exists), a `/tN/` reload changes nothing, and `/tN/` documents never scroll — `terminal-kbd.js` only parks its caret. **Nothing is relayed and nothing is learned across viewport regimes**: iOS dwells in two legitimate keyboard-up regimes (big-window `vvTop 0/vvH ~480` vs shell-scrolled `vvTop ~240/vvH ~508`), and both the earlier relayed-occlusion protocol (stale per-tab scrolls) and the learned keyboard-top prior (mid-screen bar) died on that flip — full post-mortems in `docs/design-decisions.md` (key-bar saga). Repro harness: `tests/kbd/keybar-occlusion.mjs` (live host); fixtures: `shell/keybar.test.js`.

## Utilities submenu

The **Services**, **Monitor**, **Claude Usage**, **Token Stats**, and **System Stats** features are grouped under a **"Utilities"** parent in the Start menu's **System** section — a **cascading flyout** (`#sm-util-parent` opens `.sm-sub` as a `position:fixed`, JS-placed panel **beside** the menu on desktop, or **overlaying** it as a "second page" when there's no side room; hover-opens on desktop, tap-toggles on touch). It's a flyout, not an inline expander, so opening it never grows the menu vertically. Each row has a Material 24-grid SVG icon in the same style/size as the app launchers (Claude Usage = gauge, Token Stats = trend-line, System Stats = memory chip; the Utilities parent = wrench). Claude Usage and System Stats are **toggle rows** (not apps — special-cased in the Start-menu click handler; the parent shows a `has-active` accent when either is on); **Monitor** and **Token Stats** are **normal apps** (iframes). Section membership is set by `section: 'utilities'` on the app's `APPS` entry (`buildStartMenu` routes by it, in `APPS`-key order). The three toggle/stat preferences are **shared across clients** (see the desktop-heartbeat notes above).


## Shell-wide front-end modules

**Coach tips (`shell/coach.js`)** — `window.vibeCoach(tips, opts)` holds the show-until-tapped state machine once, for every surface. Behavior: a tip **shows every time** its surface opens, has **no auto-hide**, and is dismissed by **tapping the banner itself** (no separate ×) — with a safety cap of **3** showings if never tapped. Using the gesture does *not* retire the tip. Only **one banner renders at a time**; `rotate:true` shows one tip per open so a surface with several gives each airtime. Tips live on four surfaces: **terminal** (rotating — two-finger-resize · tap-a-link→Browser · long-press→Copy, in `terminal-kbd.js`), **Files** (address-bar path jump), **Browser** (double-click/tap to re-fit · ⌨ to type), and the **Start menu** (cross-device ⏻ close, only when an app runs on another device). The Files/Browser/⏻ tips are **desktop-driven** (`coachForApp` in `desktop.html` fires them on app-activation / menu-open), so those iframes need no per-app tip code. `localStorage` keys are **versioned** (`vibetop:2fingerhint:v2`, `vibetop:kbdhint:v2`) — **to re-show a changed tip to users who dismissed the old one, bump the `:vN` suffix**. Host-wide kill switch: the Config app's *Feature hints* toggle (see `docs/apps.md` §Config app). Unit-tested in `shell/coach.test.js`.

**Shared front-end modules** — three dependency-free helpers are deployed to the web root (`shell/install.sh`), precached in `sw.js`, and guarded by `shell/js-syntax.test.js` (compile check). Two are included via `<script src>` across the app pages: `coach.js` (`window.vibeCoach`, the coach-tip state machine described above) and **`vibe-modal.js`** (`window.vibeConfirm(msg, opts)` / `vibeAlert(msg, opts)`, both returning a Promise). `vibe-modal.js` **replaces the native `window.confirm`/`alert`** — those render as off-brand OS dialogs (and appear sideways on a rotated tablet); the styled modal injects its own CSS on first use and renders inside the including document (so it covers the full-viewport app iframe it belongs to). `opts`: `{title, okText, cancelText, danger}`; `\n` line breaks honored. Used by the Logout confirm, Notes tab-close, Upload/Update/office-editor confirms. The third, **`apph.js`** (loaded only by `desktop.html`), fixes an **iOS standalone-PWA black band** after a Cloudflare Access login: after the cross-origin login, an installed PWA freezes the CSS unit `svh` *too short* (e.g. 753 on a 956px screen), so `body{height:100svh}` leaves a black band below the taskbar (a reload does NOT unfreeze it; only the first post-login session is bitten). In standalone mode `apph.js` drives `--app-h` from `max(visualViewport.height, documentElement.clientHeight)` (both measure the content area below the opaque status bar, so they can't overshoot like `100vh`/`lvh`), keeping the running MAX (reset on a width change = rotation) so the soft keyboard — which only shrinks the visual viewport — can't shrink the shell. Inert in regular Safari (`body` keeps `100svh`). Diagnostic overlay: `#vhdbg` or `localStorage.vhdbg='1'`.
